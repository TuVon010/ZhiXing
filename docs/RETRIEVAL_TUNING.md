# 邮件检索策略与可复现验证

## 为什么增加检索阶段不一定提升质量

混合检索的价值来自渠道互补：编号、精确术语适合全文检索，语义改写适合向量检索。RRF 只组合排名，不知道关键词结果是否真正相关；两路都命中的错误候选也会获得加分。CrossEncoder 的分数同样需要业务数据验证，不能无条件覆盖更可靠的初始排名。

本项目的旧策略是等权 RRF，再对前 20 条候选强制重排。邮件中的原通知和更正通知都可能与问题高度相关，单独评分不能保证更正优先。重复引用、多个必要来源、过早截断也影响最终证据覆盖。当前重排器为多语言 mMARCO MiniLM，支持中文；不能将全部损失解释为英文模型不支持中文。

[Qdrant 候选深度指南](https://qdrant.tech/documentation/search-tuning/candidate-depth/)明确区分候选覆盖与最终排序质量，更多候选并不保证融合排序更好。[Elasticsearch RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)介绍排名融合与候选窗口。这里采用分阶段评测和保守策略，而非假定所有混合链路都优于单路检索。

## 当前实现

默认 `auto` 在服务端运行，账号、时间、发件人和邮件可见状态仍在召回阶段校验。

- 全文与向量各召回 40 条，保留候选并集，最终去重后返回最多 8 条。
- 明确的字母数字编号采用完整边界匹配优先，避免 `HT-20` 匹配 `HT-204`。多个编号要求同时匹配。
- 普通语义问题保留向量前三条，再使用加权 RRF 补充来源；关键词权重 1、向量权重 4、RRF 常数 60。
- 默认不强制 CrossEncoder 重排。`hybrid` 仍提供前 20 条重排，候选尾部保留用于去重后补充。
- `keyword`、`vector`、`fusion`、`hybrid` 保留作对照和回退。指定 `mode: vector` 即恢复纯向量路径。
- Trace 的 `ranking_policy` 记录路由、权重、各候选融合分数、保护的向量头部、是否重排及重排分数。Agent 步骤保存完整可解析的摘要，详细证据和排名在审计记录中保存。
- 同分候选优先按内容哈希与已有排名稳定排序，避免数据库随机记录 ID 造成重建后的排名波动。

这些参数是当前 CPU 邮件场景的保守配置，不是行业通用最优值。保护头部也限制了融合改善语义首位结果的能力；需要独立数据证明替代策略更好后才能取消保护。最新安排类问题仍需 Agent 展开邮件线程并核对更正，不通过全局时间排序假定最新邮件就是答案。

## 本轮本地模型实测

使用真实本地 E5、Qdrant local、mMARCO CrossEncoder，未调用主生成模型或外部邮箱。

| 数据 | 策略 | 首位命中率 | Recall@5 | Recall@8 | 平均检索耗时 |
|---|---|---:|---:|---:|---:|
| 45 查询 / 60 邮件 | 关键词 | 53.3% | 86.7% | 86.7% | 4.5 ms |
| 同上 | 向量 | 71.1% | 100% | 100% | 32.0 ms |
| 同上 | 等权融合＋重排 | 64.4% | 100% | 100% | 315.2 ms |
| 同上 | auto | 71.1% | 100% | 100% | 32.3 ms |
| 35 查询（重建历史合成案例） | 向量 | 88.6% | 100% | 100% | 29.9 ms |
| 同上 | 等权融合＋重排 | 88.6% | 98.6% | 100% | 323.6 ms |
| 同上 | auto | 88.6% | 100% | 100% | 29.9 ms |

第一轮仅增加向量权重的方案在 45 条查询上首位命中率为 66.7%，未达到向量基线，故未采用为默认策略。随后加入头部保护，通过两组非退化检查。这里的提升是相对旧强制重排路径，**没有证明 auto 的首位命中率超过纯向量**。耗时是本机本轮平均值，不是服务 p95 或并发性能指标。

这些是已知、作者标注的合成回归案例，不是独立盲测。35 条案例本轮按历史案例内容重建，未复建历史实验的额外噪声邮件，因此不可与旧 80 邮件语料的指标直接比较。小语料 Recall 为 100% 不表示真实邮箱检索不会漏检。检索指标也不能推导生成答案准确率或用户任务完成率。

原有 200 个模板线程（400 封邮件）进一步复跑，每个问题需要原通知与更正通知两封证据：

| 策略 | Recall@8 | 前 8 条包含全部必要证据的查询比例 | 前 3 条包含全部必要证据的查询比例 | 平均耗时 |
|---|---:|---:|---:|---:|
| 向量 | 98.5% | 97.0% | 64.0% | 50.9 ms |
| auto | 100% | 100% | 64.0% | 49.5 ms |
| 保留尾部的融合＋重排 | 100% | 100% | 40.5% | 444.5 ms |

这里融合补充确实找回了单路向量在证据窗口中遗漏的来源；重排的前 3 条证据覆盖仍较差。`auto` 未牺牲向量头部，以较低耗时获得更完整的前 8 条证据。这 200 条只有 10 种模板，历史 optimization/holdout 分组仍共享模板，**不是新的独立保留集**，不能把 100% 当成生产质量或泛化结论。本轮更正邮件首位命中率三种模式均为 100%，不代表所有时间更正问题都已解决。

复现时发现随机记录 ID 对同分候选的排序有影响，一轮 auto 的 Recall@8 为 99.75%。修正稳定同分排序后再次运行：200 条查询的向量 / auto Recall@8 分别为 98.5% / 100%，完整证据覆盖为 97% / 100%；45 条查询的首位命中率仍为 53.3%（关键词）、71.1%（向量和 auto）。该两轮并行运行，平均耗时约 72 / 73 ms（200 条）与 45 / 47 ms（45 条），体现本机负载差异，不能将先前单轮耗时当成固定服务延迟。

## 复现

在项目根目录 PowerShell 执行：

```powershell
. .\scripts\env.ps1
& $ZhiXingPython scripts/evaluate_vector_baseline.py --modes keyword vector fusion hybrid auto
& $ZhiXingPython scripts/evaluate_vector_baseline.py --template-regression --modes vector auto hybrid
& $ZhiXingPython -m pytest tests/test_retrieval_ranking.py tests/test_mail_extended.py tests/test_mail.py -q
```

自定义数据用 `--fixture path/to/cases.jsonl`，也支持 JSON 数组。每条包含 `id`、`category`、`subject`、`messages`、`question`、`relevant_indices`；相关索引必须由标注者决定，不能根据结果回填。每次创建独立数据库和三个合成账号；UID 递增，检查入库 ID 唯一性，不接触真实邮箱数据库。

每轮在 `artifacts/mail-evaluations/vector-baseline-时间/` 保存模型 revision 与哈希、依赖版本、命令、检索源码快照、数据集哈希、逐例入库日志、实际邮件 ID 标签、逐路排名、策略分数、最终证据及数据库。第一次全量测试、失败轮次和最终测试分别归档，目录被 Git 忽略。

## 工程验证边界

本轮检索与 Agent 定向测试 140 项通过；会话追问、来源跳转、重命名及回收站恢复的浏览器测试 2 项通过；前端类型生成与构建通过。

最终全量回归：299 项通过、7 项失败。使用修改前 HEAD 的独立源码快照复跑得到相同 7 项失败，涉及旧审批/日程/跟进测试与摘要文案预期。不能将全量结果写成全部通过；详见本地 `artifacts/retrieval-before-full-regression-20261008.xml` 与 `artifacts/retrieval-release-regression-20261008.xml`。

最终定向复跑为 `artifacts/retrieval-targeted-release-20261008.xml`。包含截图快照的成功浏览器 Trace 保存在 `artifacts/browser/retrieval-trace-20261008/results/`；完整应用检索 Trace 在对应隔离测试数据库中。测试中曾有断言固定引用“块 0”，排序调整后可能返回另一重叠块，已改为引用真正传入模型的证据，仍要求引用存在且上下文正确压缩。

后续质量门槛应使用脱敏真实邮件、独立标注的新查询、线程级分组的保留集，并加入无答案、近似编号、多个证据、冲突更正和长附件。逐阶段比较候选 Recall、首位命中率、nDCG、完整证据覆盖及延迟，最后再评估生成答案的引用支持率。只有主模型也参与评测，才能证明回答效果改善。
