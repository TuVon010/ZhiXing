# 知行 RAG 评测报告

> 生成时间：2026-09-23
> 模型：intfloat/multilingual-e5-small（嵌入）+ cross-encoder/mmarco-mMiniLMv2-L12-H384-v1（重排序）
> 数据：17 封合成邮件，20 条评测查询
> 环境：CPU 模式，Windows，SQLite FTS5 + NumPy 向量

> 历史基线说明：本报告的实际运行发生在 Qdrant local 接入之前；向量阶段使用 NumPy 精确余弦。保留原始数据和数字作为历史研究记录，它们不代表当前 Qdrant 后端性能。要比较当前实现，需固定本报告的语料、查询与标签，重新运行并另存新报告。

## 一、评测设计

### 数据集
- **邮件**：17 封合成邮件，覆盖导师/老板/实验室/HR/同事/广告/事务 7 类发件人
- **查询**：20 条，分为 10 个类别：
  - exact（精确术语）3 条
  - semantic（语义改写）3 条
  - multi（多跳组合）2 条
  - negation（否定排除）1 条
  - temporal（时间敏感）2 条
  - sender（发件人相关）2 条
  - attachment（附件相关）1 条
  - todo（承诺待办）2 条
  - vague（模糊查询）1 条
  - technical（技术术语）2 条
  - thread（跨线程）1 条
  - numeric（数字金额）1 条

### 评测指标
- **Recall**：命中的期望发件人比例（衡量是否找全）
- **Precision**：命中结果中期望发件人的比例（衡量是否找准）
- **Latency**：单次检索延迟（ms）
- **Recall@1**：完全命中所有期望发件人的查询比例

### 对比模式
1. **关键词检索**：SQLite FTS5 + 中文预分词（jieba），模型不可用时的降级模式
2. **混合检索**：关键词（40条）+ 向量（40条）→ RRF 融合（20条）→ 重排序（Top 8）

## 二、整体结果

| 模式 | Recall | Precision | Latency | Recall@1 | 降级 |
|------|--------|-----------|---------|----------|------|
| 关键词 | **0.950** | **0.411** | **2.8ms** | 0.95 | 是 |
| 混合+重排序 | 0.950 | 0.235 | 409.0ms | 0.95 | 否 |

**关键发现**：
- 两种模式 Recall 相同（0.95），说明关键词在小数据集上已经能覆盖大部分查询
- 混合模式 Precision 更低（0.235 vs 0.411），因为向量召回了更多语义相关但发件人不匹配的结果
- 混合模式延迟高 146 倍（409ms vs 2.8ms），主要来自 CPU 上的向量编码和重排序
- **语义类查询是混合模式的核心价值点**（见下文分类分析）

## 三、分类对比

| 类别 | 关键词 Recall | 混合 Recall | Δ Recall | 关键词 Precision | 混合 Precision |
|------|-------------|------------|----------|-----------------|---------------|
| exact（精确术语） | 1.000 | 1.000 | +0.000 | 0.556 | 0.189 |
| semantic（语义改写） | 0.667 | **1.000** | **+0.333** | 0.444 | 0.217 |
| multi（多跳组合） | 1.000 | 0.750 | -0.250 | 0.367 | 0.283 |
| negation（否定排除） | 1.000 | 1.000 | +0.000 | 0.286 | 0.333 |
| temporal（时间敏感） | 1.000 | 1.000 | +0.000 | 0.155 | 0.200 |
| sender（发件人相关） | 1.000 | 1.000 | +0.000 | 0.143 | 0.225 |
| attachment（附件相关） | 1.000 | 1.000 | +0.000 | 0.143 | 0.167 |
| todo（承诺待办） | 1.000 | 0.500 | -0.500 | 0.400 | 0.200 |
| vague（模糊查询） | 1.000 | 1.000 | +0.000 | 0.286 | 0.400 |
| technical（技术术语） | 1.000 | 1.000 | +0.000 | 0.750 | 0.183 |
| thread（跨线程） | 1.000 | 1.000 | +0.000 | 0.286 | 0.400 |
| numeric（数字金额） | 1.000 | 1.000 | +0.000 | 1.000 | 0.200 |

### 核心结论

1. **语义改写类查询提升显著**：semantic 类 Recall 从 0.667 提升到 1.000（+33.3%）
   - 例："什么时候交作业" → 命中"实验报告要求"（关键词无法匹配"作业"和"报告"）
   - 例："项目进度安排" → 命中"项目进度汇报"和"下周工作安排"

2. **精确术语类关键词更优**：exact 和 technical 类的 Precision 关键词更高
   - 关键词对"GPU 显存"、"数据预处理"等专业术语匹配更精准
   - 向量检索会引入语义相近但术语不同的干扰结果

3. **多跳和待办类混合模式下降**：可能是向量召回稀释了关键结果
   - todo 类 Recall 从 1.0 降到 0.5，需要后续优化重排序权重

4. **小数据集局限**：17 封邮件的语料量较小，向量检索的优势在更大语料上会更明显

## 四、延迟分析

| 阶段 | 关键词 | 混合 |
|------|--------|------|
| FTS5 检索 | ~1ms | ~1ms |
| 向量编码（CPU） | - | ~200ms |
| 向量检索（NumPy） | - | ~50ms |
| RRF 融合 | - | ~1ms |
| 重排序（CrossEncoder） | - | ~150ms |
| **合计** | **2.8ms** | **409ms** |

- 嵌入模型在 CPU 上单条编码约 10-20ms，批量编码可优化
- 重排序是最大开销（150ms），可考虑缓存或减少重排序候选数
- 生产环境可使用 GPU 或 ONNX 量化加速

## 五、改进建议

1. **自适应检索策略**：查询包含明确专业术语时优先关键词，语义模糊时启用向量
2. **重排序权重调优**：当前 todo/multi 类下降，可调整 RRF k 值和重排序 Top-K
3. **查询扩展**：对语义查询做同义词扩展后再走关键词，可能比纯向量更高效
4. **向量缓存**：对重复查询缓存向量编码结果
5. **更大评测集**：当前 17 封邮件语料较小，建议扩展到 100+ 封以验证规模化效果
