# 知行邮件 Agent 产品与业务评估

评估日期：2026-09-23。范围是当前邮件工作台、单机 API/Worker、多邮箱数据流和离线演示；外部邮箱凭证与主模型没有做真实联调。

## 当前成熟度结论

当前更准确的定位是“功能完整度较高的个人邮件 Agent MVP / 学习型工程原型”，不是已经生产验收的产品。代码具备从收取、过滤、检索、Agent 多轮决策、动作提案、审批到受控执行与 Trace 的闭环；真实邮箱、主模型服务、长期稳定性及真实业务价值还缺验证。完整功能清单见本机面试学习资料的“邮件业务与产品价值”。

## 当前业务闭环

添加邮箱并测试连接 → 明确启用收取 → 首次建立 UID 基线 → 按账号收取和过滤 → 建立线程及本地索引 → 用户选择邮箱范围后搜索或询问 Agent → 生成待办/提醒/草稿 → 高风险发送进入审批 → 查看 Trace 和费用统计。

待办、审批已内置在邮件工作台，不再导航到旧版工作台。邮件回复的审批固定绑定发件账号和草稿版本；改动草稿后旧审批失效。飞书适配器、入口、设置和依赖已移除。本地旧消息和运行记录保留用于历史追溯，连接状态和设置记录已清理；历史归档材料中仍能看到当时的集成测试名称。

## 合理性与易用性

产品定位比原通用个人助理更清楚：邮件是唯一业务来源，过滤、检索、跟进和发送都能围绕线程证据操作。账号范围可见且需要显式选择跨账号检索；收取、索引和模型分析分开，减少首次连接造成的历史邮件和模型调用失控；过滤/归档只影响本地，不删除服务器内容；发送前人工核对，适合承载个人邮件。

推荐的新用户路径：先导入演示数据熟悉邮件、证据引用、待办和审批；然后添加一个测试邮箱、只做连接测试；确认账号后再启用接收；先预览一小段历史，再决定是否导入。自动分析默认关闭，适合先观察 Trace 与模型预算，再选择启用。

当前主要上手成本是设置项偏多：IMAP/SMTP、扫描额度、导入区间、过滤 JSON、模型计价都集中在同一套设置体验里。非技术用户不应一开始改过滤 JSON 或自动分析额度；建议后续增加分步账号向导、服务商配置说明、连接错误的可操作指引和“先只收取、不分析”的明确开关说明。待办完成属于中风险变更，需要审批，这是安全一致的做法，但个人使用会多一步；若要简化，可增加“用户直接点击即明确授权”的专用操作并在审计中保留该确认。

## 验证证据

- 后端：221 项测试通过；另有 1 条第三方 AnyIO 弃用警告。
- 前端：TypeScript 检查和 Vite 生产构建通过；2 条 Playwright 测试通过，覆盖新版导航、邮件草稿审批、待办审批、Trace 导出和计价设置。
- 规则评测：120 条合成回归样本，训练集与保留集的计划工具、风险、澄清和字段检查均为 100%。这是离线规则回归，不代表真实模型准确率。
- 检索评测：当前 Qdrant 本地模型运行 17 封合成邮件、20 条查询，关键词与混合+重排的发件人级 Recall 均 0.95；混合 Precision 较低（0.235 vs 0.411）、延迟较高（278ms vs 1.9ms）。样本和标签粒度有限，不可解释为真实收件箱质量或普遍性能提升；逐例结果在 `artifacts/rag-evaluations/20260923-052659-365160/`。
- 最新完整测试命令、依赖快照、源码快照、JUnit、逐例评测、浏览器截图/录像保存在 `artifacts/test-runs/20260923-125324-834700/`。另在 `artifacts/mail-recovery/20260923-124429/` 做过本地 E5 + CrossEncoder、Qdrant 持久化检索与恢复演练。
- 本机服务已启动并通过健康检查；当前数据库没有配置新的多邮箱账号。SMTP/IMAP 和主模型真实联调尚未验证。

## 仍需谨慎的边界

本地向量检索不表示全链路离线；被选择的邮件证据会发送给配置的模型服务。SMTP 接受不等于最终投递；发送结果不确定时必须先去邮箱服务端核对。附件解析覆盖受限文本文件，不含 OCR。浏览器和 120 条规则评测不能替代真实邮箱权限、授权码、主模型质量及长时间运行的验收。

历史 RAG 报告中的 NumPy 精确余弦和延迟数据采集自 Qdrant 接入前，只能作为旧版本基线；不能据此评价当前 Qdrant 的性能。应使用相同语料和查询重跑并报告版本差异。
