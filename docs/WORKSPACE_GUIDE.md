# 知行工作台：使用、结构与调试

本指南对应当前多邮箱工作台。系统是本地单用户 MVP，真实邮箱权限、主模型效果仍需要用自己的测试账号验证。

## 先走通一次业务

1. 在“邮箱账号”保存账号并测试连接，然后启用收取。首次连接只建立基线；历史资料在“收取与导入”预览后导入。
2. 在“收件箱”阅读正文和线程。过滤是本地状态变化，原邮箱不删除；误过滤到“过滤箱”恢复。
3. 在“邮件 Agent”明确选择可读取的邮箱，再提问。需要依据时使用检索；生成草稿不代表已发送。
4. 在“回复草稿”核对发件账号、收件人、抄送和正文，保存后点击“准备发送”，在同一页完成最终核对并确认发送。之后修改收件人、主题或正文必须重新确认。
5. 在草稿页核对当前版本并最终确认发送，点击“查看发送结果”查看真实执行 Trace。确认发送不等于发送成功，SMTP 接受也不等于送达。
6. 在“待办与跟进”“日程”查看已生效工作事项。在“通知与提醒”查看到期提醒和执行结果，并标记已读。

演示模式可导入合成邮件；模拟发送会明确标记，不能当作真实收发验收。你主动创建/修改的日程本地直存、立即生效；含糊或冲突的建议进入“待核实建议”。当前提醒在 Web 通知中心展示，不是 Windows 系统通知，也不会自动向邮箱外发。

## Trace 怎么读

入口包括：运行记录、Agent 会话、发送确认、草稿发送结果、待办来源、通知中的执行记录。

- `assistant_turn.id`：一轮 Agent 决策，保存请求、证据、记忆快照、工具步骤。
- `run.id`：一组受控动作，保存风险判断、审批、执行结果与 LangGraph 检查点。
- `message.metadata.assistant_turn`：动作回到父 Agent 的关联；Agent 草稿经用户编辑后仍保留来源。
- `action.id`：执行账本幂等键。相同动作重启后不会重复执行已确认的副作用。

`GET /api/mail/traces/{id}` 接受 turn 或 run ID，返回父轮次和关联动作，汇总审计、模型调用及计价。它复用原 `tracing.detail()`，没有复制执行引擎。模型调用按 ID 去重，费用仍保留币种和未知状态。导出可能包含邮件正文，按私人资料保存。

时间线只记录显式请求和工具结果，不包含模型隐藏思维链。窗口打开时轮询刷新，关闭即停止；动作列表与 Agent 状态分开显示，避免把“对话完成”误当成“任务执行成功”。

## 代码应该从哪里读

| 代码 | 职责 | 学习重点 |
| --- | --- | --- |
| `frontend/src/MailApp.tsx` | 导航、账号选择、页面装配 | 页面壳不写各业务表单 |
| `frontend/src/mail/useMailWorkspace.ts` | 会话、数据刷新、跨页操作 | UI 状态和异步请求；Context 只在工作台内共享 |
| `frontend/src/mail/*Page.tsx` | 收件箱、账号、Agent、草稿等页面 | 读写 API、表单校验、用户反馈 |
| `frontend/src/MailTrace.tsx` | 时间线、执行结果、模型调用与导出 | 可观测性和操作状态分离 |
| `frontend/src/MailActivity.tsx` | 分页运行记录与通知 | 账号范围、轮询清理、未读状态 |
| `backend/mail_api.py` | 邮件核心接口 | API 校验、入队与读取 |
| `backend/mail_observability.py` | 工作台查询、Trace 聚合、通知、日程操作入口 | 只读聚合复用，写动作交给统一执行链 |
| `backend/mail_assistant.py` | 有界决策循环、草稿、记忆快照 | 工具范围、幂等、动作结果查询 |
| `backend/worker.py` | 调度和两队列轮转 | 邮件积压不能无限压住审批执行 |
| `backend/mail_worker.py` | 邮件任务领取、续租、批次续接 | 持久队列、状态迁移与错误 |
| `backend/runtime.py` / `tools.py` | LangGraph、审批、账本、确定性工具 | 崩溃恢复、参数版本和事务 |

先学业务状态和调用关系，再读 RAG 排名实现。无需一次理解全部模块。前端保留部分历史宽类型和共享状态，未来可以按实际维护成本逐步收紧；不要为了“架构感”再增加一套执行框架。

## 旧代码如何处理

复用：LangGraph 审批暂停恢复、执行账本、风险策略、审计、计价、Skill/Parser 后端和已积累测试。它们是邮件业务的底座。

移除：旧版 UI、旧版单邮箱直接 SMTP 发送、失效样式。`channels.py` 仅保留共享的“外部结果不明”异常契约。旧 `.env` 邮箱字段仍用于显式迁移读取，不再构成直接发送通道。

保留：已有业务记录、checkpoint、历史测试归档、升级复核入口。清理旧代码不等于删除用户数据；旧运行的真实发送也必须满足当前多邮箱草稿校验。历史设计副本不再作为当前使用说明。

## 四个调试实验

1. **确认不等于成功**：创建草稿，完成最终确认，分别导出排队中和执行后的 Trace。比较 `run.status`、`outcomes`、账本结果和草稿状态。
2. **父子运行关联**：让 Agent 生成待办或草稿，记下 turn ID。在运行记录进入子 run，确认能看到父 Agent 的检索和模型调用。确认人工编辑草稿后关联还在。
3. **提醒闭环**：在隔离测试库创建过期提醒，调用 `tick(db)` 两次，应只有一条提醒通知。标记已读两次仍然是已读，切换邮箱不能看到其他邮箱提醒。
4. **队列公平性**：让邮件队列持续有任务，同时提交发送动作。`work_cycle()` 每轮分别尝试动作和邮件队列，验证动作能前进。这不是抢占式调度；正在执行的网络/模型调用仍受各自超时约束。

对应测试是 `tests/test_mail_workspace.py` 和 `frontend/e2e/workspace.spec.ts`。这些测试使用合成数据与模拟服务。

## 研究留档

运行 `scripts/test.ps1` 生成独立 `artifacts/test-runs/<时间戳>/`。查看 `manifest.json`、`backend-junit.xml`、各阶段日志、测试数据库、源码快照、浏览器截图/录像/Trace。失败轮次不覆盖；复制数据库研究，不能修改正式邮箱数据来做实验。

工程回归通过不等于真实 Agent 质量达标。真实试用至少记录：漏掉多少明确任务、误过滤多少邮件、引用是否支持答案、草稿需要修改几处、完成一个邮件任务花多久。检索 Recall、模型用量与端到端任务完成率是不同指标。
